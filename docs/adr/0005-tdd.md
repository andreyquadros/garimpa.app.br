# ADR-0005 — Desenvolvimento guiado por testes (TDD) em todo o código

| | |
|---|---|
| **Status** | Aceita (out/2026) |
| **Decisão** | Toda mudança de comportamento, na API e na interface, segue o ciclo **vermelho → verde → refatorar**. |

## Contexto

As pepitas vão virar dinheiro na fase 2: livro-razão, carência, estornos e antifraude não podem quebrar em silêncio. Hoje há 41 testes na API e 5 no web.

## Decisão

- **Ciclo:** o teste é escrito antes e precisa falhar pelo motivo esperado; depois o código mínimo que o faz passar; depois a refatoração com os testes verdes. Teste e implementação vão no mesmo commit (nenhum commit com teste falhando).
- **API:** testes contra um PostgreSQL 18 real, sem simular o banco. Regras de economia e antifraude são verificadas pelos efeitos no livro-razão.
- **Interface:** testes de componente com Testing Library e `user-event`, verificando comportamento (o que a pessoa vê e faz), sem snapshots. Lógica pura vai para `web/src/lib/` com teste unitário.
- **Aspecto visual** (layout, cores, animação) não é coberto por teste unitário: é verificado rodando o app, e o PR diz como.
- **Bug:** primeiro um teste que reproduz o bug e falha; depois a correção.
- **Ponta a ponta:** um teste com Playwright do fluxo principal (entrar → abrir missão → enviar evidência → confirmar → aceitar), atualizado quando esse fluxo mudar (`web/e2e/fluxo-principal.spec.ts`, roda no CI no job `e2e`).

## Opções comparadas

| Opção | A favor | Contra |
|---|---|---|
| **TDD em tudo** | Cobertura alta e testes que realmente descrevem o comportamento | Mais lento, sobretudo na interface |
| Testes só nas regras e nos bugs | Foco no que envolve dinheiro | Interface sem rede de proteção |
| Testes quando fizer sentido | Mais rápido | Risco alto nas regras de dinheiro |

## Consequências

- Componentes precisam ser escritos de forma testável (props claras, lógica fora do JSX).
- O Playwright, hoje usado só em `web/scripts/smoke-demo.mjs`, é dependência de desenvolvimento (implantado em out/2026).
